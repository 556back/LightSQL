## 销售经营120题

- [问题清单](examples/sales-acceptance/questions.md)：可直接阅读的120题及预期动作。
- [题集 JSON](examples/sales-acceptance/questions.json)：符合现有 `DatasetInput` 契约，包含参考计划、参考 SQL、预期列/结果、标签及集合。
- [参考 SQL](examples/sales-acceptance/reference.sql)：100道可回答题的 PostgreSQL 只读参考查询。
- [冻结数据](examples/sales-acceptance/snapshot.json)：既有 M03 的5笔订单和3个客户，无真实业务数据。
- [参考结果核验记录](examples/sales-acceptance/reference-check.json)：独立 Decimal 计算、内存 SQLite 参考 SQL、转换后的生产语义编译 SQL，以及本地 PostgreSQL 参考 SQL 交叉核对。

题集为100道可回答、10道应澄清、10道标准指标模式下不支持；开发/留出各60题。涵盖销售总额、退款金额、净销售额、支付订单数、客单价，以及日期范围、逐日/区域/渠道分组、客户排行、实体筛选和追问。所有业务金额按已支付订单口径，退款归属原订单日期；取消订单排除，客户按租户与客户编号复合键关联。

100道可回答题来自50个指标/场景组合，每个组合两个问法。相同筛选维度与改写族整体放在同一集合，40道可回答题含实体筛选，其中20道附带历史追问。另有2道同义实体歧义题。当前留出题与答案随仓库公开，而且开发/留出动作分布并未平衡，**只用于合成留出流程验证，不是保密、分层的业务盲测**；不能把120个条目解释成120种独立复杂业务意图。

金额由独立 Python Decimal 算法生成参考值；比例型客单价的允许误差为 `0.00000001`，其余题集数值误差为零。离线 SQLite 的浮点对照按8位小数规范化，正式结果评分仍使用题集声明的容差。参考 PostgreSQL 查询已在同一只读、可重复读事务中核对全部源表快照，然后100/100通过。该事务不写业务表。MySQL/Oracle 尚未执行这份销售120题；之前75项三库合成测试是另一套数据与证据。

本地 `/quality` 已新增题集“**M07 销售经营120题 · 合成留出验证**”，绑定既有“M05 合成销售问答”的当前发布版本。题集 ID 为 `88b68899-0d91-44f1-8817-7908900487cd`，已重新导出并逐字段核对；可直接供运行器使用的导出文件是 `.local/sales-120-export.json`。没有生成问答模型评测分数、执行真实模型调用、改动原有主题/授权或模型配置。

仓库 JSON 中的零 UUID 是可移植模板。换环境时必须绑定该环境的实际主题 ID、版本，并重新核对数据快照；不要把模板直接当作已有主题的可运行导出文件。

## 默认15秒预算的三轮复测

查询完成事件新增纯数字分阶段计时：授权准备、调用spawn、子进程入口前启动、子进程连接/查询/取数/清理以及Worker总时长。没有SQL、凭证或结果内容，不改现有API数据结构；所有异常仍遵循原有清理未确认处理。

`scripts/module7_capacity.py` 现在默认15秒，支持 `--timeout-seconds 15/20/30`、`--repeats 1..5` 及新报告路径。默认自动生成新文件名，显式路径已存在则拒绝，原失败证据得以保留。每轮创建独立元数据库，两个独立Worker竞争同一个全局调度门；运行期间的主环境服务和配置不变。

| 轮次 | 成功 | 含排队P50 | 含排队P95 | 子进程启动范围 | 子进程执行范围 |
|---|---:|---:|---:|---:|---:|
| 1 | 10/10 | 15.630秒 | 22.458秒 | 4.089–7.612秒 | 0.174–0.640秒 |
| 2 | 10/10 | 30.482秒 | 37.299秒 | 3.841–12.374秒 | 0.158–1.826秒 |
| 3 | 10/10 | 12.090秒 | 18.094秒 | 5.039–5.750秒 | 0.171–0.515秒 |

三轮峰值均为全局5、每源2、每人不超1，无超额，Worker均正常退出；25项×三库亦全部通过。证据 `.local/module7-capacity-default-repeat.json`。子进程启动计时包含操作系统调度及模块导入；执行计时包含连接和清理，并非纯SQL耗时。各计时项存在包含关系，不能直接相加。

结果表明此宿主环境的启动/排队开销值得优先排查，但不证明历史超时只有一个原因。本轮没有修改默认查询预算、复用跨用户连接或放宽隔离。两轮P50高于原规划15秒目标，且测试是10请求突发、小数据、无模型，**生产容量及持续5并发仍未验收**。后续应固定目标硬件与负载，先比较发布镜像下冷/热启动和模块加载，再决定是否需要受控预热方案。

复测命令（每次使用新的输出文件名）：
