# LightSQL 本地开发启动教程

适用版本：2026-09-08。命令按 **Windows PowerShell** 编写。仓库以 `D:\Projects\LightSQL` 为例；路径不同时自行替换。每条命令成功后再执行下一条。

推荐开发方式：Docker 只运行 PostgreSQL / MySQL，API、三个 Worker 和 Vite 在本机运行。只想体验系统、不修改代码时，使用 [完整系统启动教程的方案 A](系统启动教程.md)，全部服务在容器中运行，入口为 18000。

## 1. 准备依赖和代码

需要 Git、Docker Desktop（Linux 容器）、Python 3.14、uv、Node.js、Bun。仓库要求 Python `>=3.14,<4.0`；本次构建使用 Node 22.18.0，CI 配置使用 Bun 1.3.12。建议沿用这些版本和已提交锁文件。

```powershell
git --version
docker version
docker compose version
uv --version
node --version
bun --version
```

Docker 必须显示 Server 信息。首次安装依赖需要可访问镜像与包仓库。`bun` 找不到时先安装 Bun 并重新打开 PowerShell；不要用 npm install 替代仓库的 Bun 锁文件安装流程。

**全新电脑**：

```powershell
Set-Location D:\Projects
git clone --branch codex/dev-frontend https://github.com/556back/LightSQL.git
Set-Location D:\Projects\LightSQL
uv python install 3.14
uv sync --frozen --package app
bun install --frozen-lockfile
```

**当前电脑已有仓库**：直接进入项目目录，无需再次克隆。已有可用 `.venv` 与 `node_modules` 时可跳过安装；更新依赖后再执行上述两个 sync/install 命令。不需要手动激活虚拟环境，后面的命令显式指定 Python。

根目录 `.env` 和前端 `.env` 不随仓库分发。开发脚本会从 `.local/demo.json` 配置后端，因此本教程不要求创建根 `.env`。`*.env.example` 仅包含公开示例；不要将业务连接密码或模型密钥写入示例。

## 2. 准备并启动数据库

在项目根目录执行：

```powershell
.venv\Scripts\python.exe scripts/module1_demo.py prepare
docker compose --env-file .local/demo.env -f compose.demo.yml up -d postgres mysql
docker compose --env-file .local/demo.env -f compose.demo.yml ps
```

`prepare` 生成 `.local/demo.json` 和 `.local/demo.env`，重复执行保留原随机密码及加密密钥。已有数据库必须保留原文件；重新生成凭据不会更改现有数据库卷的密码，也无法解密旧配置。

| 服务 | 本机地址 | 用途 |
| --- | --- | --- |
| PostgreSQL | `127.0.0.1:15432`，数据库 `lightsql_demo` | 元数据库，同时承载隔离的合成业务 schema |
| MySQL | `127.0.0.1:13306`，数据库 `sales_demo` | 合成业务库 |

等待数据库就绪：

```powershell
docker compose --env-file .local/demo.env -f compose.demo.yml exec postgres pg_isready -U postgres -d lightsql_demo
docker compose --env-file .local/demo.env -f compose.demo.yml logs --tail 30 mysql
```

PostgreSQL 应显示 accepting connections，MySQL 日志应出现 ready for connections。首次启动可能需要等待。Oracle 是可选接入源，本教程无需启动 extended 配置中的其他数据库。

**第一次初始化**：

```powershell
.venv\Scripts\python.exe scripts/module1_demo.py seed
```

此命令升级元数据库结构、创建初始管理员、合成订单表、只读账号，并登记两个演示数据源。不会自动创建完整主题、业务权限和模型配置。若数据库尚未就绪导致连接失败，等待就绪后重跑。

**已有环境更新代码后**，只升级结构：

```powershell
.venv\Scripts\python.exe scripts/module1_demo.py migrate
```

## 3. 先构建一次前端

后端会挂载 `backend/app/frontend`。全新克隆没有该目录中的构建产物，先构建再启动 API：

```powershell
$env:VITE_API_URL = '/'
npm --prefix frontend run build
```

构建包含 TypeScript 检查，产物由 API 同源提供。`VITE_API_URL=/` 同时适用于 Vite 代理和 8000 同源页面，避免把旧的固定 API 地址打入构建。

## 4. 启动四个后端进程

打开四个 PowerShell 终端。每个终端都先执行 `Set-Location D:\Projects\LightSQL`，然后分别执行对应命令。终端持续运行是正常现象。

| 终端 | 命令 | 作用 |
| --- | --- | --- |
| 1 | `.venv\Scripts\python.exe scripts/module1_demo.py api` | API、管理页及问数页，监听 8000 |
| 2 | `.venv\Scripts\python.exe scripts/module1_demo.py worker` | 数据目录同步 |
| 3 | `.venv\Scripts\python.exe scripts/module1_demo.py query-worker` | 只读查询执行 |
| 4 | `.venv\Scripts\python.exe scripts/module1_demo.py integration-worker` | 外部 API / 嵌入任务编排 |

这些命令会统一加载 `.local/demo.json` 中的配置。不要只启动 API，否则目录同步或查询可能一直排队。不要将 `startup.env` 的密钥与 demo 数据库混用。

## 5. 启动前端热更新并登录

第五个终端执行：

```powershell
Set-Location D:\Projects\LightSQL
$env:VITE_API_URL = '/'
npm --prefix frontend run dev -- --port 5173 --strictPort
```

日常开发访问 **http://localhost:5173**。Vite 绑定本机回环地址，将 `/api` 转发到 `127.0.0.1:8000`。使用 localhost 与开发脚本配置的前端来源保持一致。

| 入口 | 地址 |
| --- | --- |
| 前端热更新 | http://localhost:5173 |
| 完整构建页面 / 嵌入联调 | http://127.0.0.1:8000 |
| API 文档 | http://127.0.0.1:8000/docs |
| 健康检查 | http://127.0.0.1:8000/api/v1/utils/health-check/ |
| 质量评测与运维 | http://localhost:5173/quality |
| 外部系统接入 | http://localhost:5173/integrations |

本地合成演示账号：`admin@lightsql.example.com`，初始密码 `LightSQL-Demo-2026!`。这是源码内公开的演示凭证，仅用于本机合成数据；接入真实数据前在用户设置中修改。已有账号使用实际修改后的密码，重跑 seed 或修改环境变量不会重置它。

开发脚本禁用邮件发送与 Sentry，公开注册默认关闭。忘记密码邮件不会在这套演示环境中自动发出；普通用户由管理员创建。

## 6. 从“启动成功”到“可以问数”

1. 登录后进入“数据源”，验证两个演示连接；新增业务源时使用只读账号。
2. 在“数据目录”发起同步，确认任务完成且能看到表、字段。
3. 创建业务主题，配置关系、指标和维度，校验并发布。
4. 创建普通用户，将其加入主题，并配置指标、维度与行范围查询权限；自由探索需要逐列授权。
5. 用普通用户执行结构化查询，核对结果。
6. 需要自然语言问数时，在“模型配置”填写供应商地址、模型名和 API Key，验证并启用，再进入“智能问数”。真实模型调用可能产生费用。
7. 需要外部接入时，在“外部系统接入”配置应用和主题、执行身份及来源，按页面自检。详见 [外部系统接入开发与使用](外部系统接入开发与使用.md)。

默认业务主机白名单是 localhost / 127.0.0.1。接其他内网数据库需调整 `scripts/module1_demo.py` 中 `configure()` 的 `DATASOURCE_ALLOWED_HOSTS` 并重启 API 和 Worker；真实内网配置应留在个人本地修改或独立的私有配置中，不提交。非预设模型服务可在各后端终端启动前设置 `MODEL_GATEWAY_ALLOWED_BASE_URLS`，内容为精确 base URL 的 JSON 数组，所有进程保持一致。API Key 在系统中录入，不写入前端 `VITE_*` 变量。

## 7. 每天怎么启动、修改和停止

已经完成初始化后，每天只需要：

1. 启动 Docker Desktop，并执行第 2 节的 `up -d postgres mysql`。
2. 打开四个终端，执行第 4 节的四条命令。
3. 打开第五个终端启动 Vite，访问 5173。

修改前端代码会由 Vite 热更新；8000 页面需重新执行第 3 节构建并刷新。当前 `api` 命令没有自动 reload，修改后端代码后在相关终端 Ctrl+C 再启动，Worker 也需重启。更新代码含数据库迁移时先备份、停后端进程、执行 migrate，再启动进程。

停止时在五个终端分别 Ctrl+C，然后停止数据库，保留数据：

```powershell
docker compose --env-file .local/demo.env -f compose.demo.yml stop postgres mysql
```

不要用 `down -v` 做重启，它会删除数据库卷。备份数据库时同时保存匹配的 `.local/demo.json`，参见 [运维手册](M07运维手册.md)。

## 8. 验证和排错

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/utils/health-check/
# 隔离模块回归：不执行顶层会清理 User/Item 的数据库夹具
.venv\Scripts\python.exe scripts/module1_demo.py test
```

健康检查应返回 `true`。三个 Worker 还需分别通过目录同步、结构化查询、外部任务验证，API 健康不代表完整业务流程通过。本次提交前模块回归 **289 项通过**，TypeScript 与 Vite 构建通过。

| 问题 | 处理 |
| --- | --- |
| 找不到 uv / bun / node | 安装相应工具，重新打开终端确认 PATH |
| Python 版本不符 | 执行 `uv python install 3.14`，再 `uv sync --frozen --package app` |
| Docker 连接失败 | 启动 Docker Desktop，确认 Linux 引擎和 Server 正常 |
| 15432 / 13306 / 8000 / 5173 被占用 | 检查已有服务；不要重复启动。数据库端口若修改，还须同步脚本连接配置 |
| seed 连接被拒绝 | 等两个数据库初始化完成后重跑 |
| API 找不到前端目录 | 先执行第 3 节构建 |
| 页面可打开，API 请求失败 | 前端终端设置 `VITE_API_URL=/` 后重启 Vite / 重新构建，确认 8000 可用 |
| 目录同步 / 查询一直排队 | 检查对应 Worker 终端；确认使用同一元数据库和密钥 |
| 加密内容无法读取 | 恢复原 `.local/demo.json`，不要随机更换旧库密钥 |
| 登录后没有主题或数据 | 检查主题发布、成员和查询授权；管理员身份不替代普通用户权限验证 |
| 8000 和 18000 内容不同 | 它们分别对应 demo 和全容器环境，数据库独立 |

## 9. 提交时哪些内容应保留在本机

`.env`、`frontend/.env`、`.local/`、私钥、数据库文件与备份、日志、依赖目录及构建产物均已加入忽略规则；Docker 构建上下文也排除本地配置与密钥。仓库只提交脱敏的 `.env.example` / `frontend/.env.example`，CI 从示例建立临时配置。

提交前查看：

```powershell
git status --short
git diff --cached --stat
git check-ignore .env frontend/.env .local/demo.json .local/startup.env
```

忽略规则不能保护已被跟踪的文件，也不能识别源码中新粘贴的密钥；仍应检查暂存内容。不要把真实模型 Key、连接密码、业务导出或包含凭证的截图放入 docs/examples。已有合成示例与公开 DuSQL 数据保留在仓库中。
