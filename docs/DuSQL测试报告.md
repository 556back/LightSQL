## 数据与 SQL 问题

逐题错误见 [开发集结果 CSV](examples/dusql-verification/dev-results.csv)，机器可读统计及输入 SHA-256 见 [summary.json](examples/dusql-verification/summary.json)。错误可能叠加，以下按首先遇到的错误举例，不作为互斥分类总计。

- 别名使用不一致。例如 `qid000035` 声明 `生涯之最 AS T1`、`篮球运动员 AS T2`，关联条件却继续写原表名。原参考查询和编译器均不能直接执行该写法。
- 100 题在 PostgreSQL 首先报 `TIME_NOW` 字段不存在；没有擅自给该占位符指定年份。
- 28 题把 `T1` 等外层别名用于子查询的 `FROM`，无法绑定到数据库实体；另外2题语法解析失败。
- 开发集17个数据库中，151个标注为数值的列包含非纯数值内容，如百分号、中文单位。按本轮保留值的类型策略，145题首先遇到 `avg(text)`、82题遇到 `sum(text)`、104题遇到 `text - text` 错误；还有文本与数值比较等错误。

这些结果包含**原始参考 SQL 问题、类型映射和跨方言兼容限制**，不能全部归因于 LightSQL 缺陷。修复参考 SQL、单位换算、日期解释和字段类型都需要建立明确规则后另存修订版本，保留当前原始基线。

## 测试方法和边界

读取原始 JSON，在内存 SQLite 和本地 PostgreSQL 会话临时表中装载快照。源文件未修改，现有数据库业务表、主题、权限和模型配置未修改；PostgreSQL 临时表事务在结束时回滚。

参考 SQL 经 SQLGlot 的 MySQL 解析器读取，再生成目标方言；`==`、引号等语法由解析器规范化。用于 LightSQL 的输入只把中文物理表名映射为 `t0`、`t1` 等合法逻辑名称，保留别名和筛选值，调用实际 `compile_sql`。没有用参考答案替换模型输出来冒充模型测试。

SQLite 数值列使用 NUMERIC affinity，保留非数值字符串；关闭双引号字符串回退，避免不存在的字段被当成字符串执行。PostgreSQL 只有整列所有非空值均为有限数值时才使用 NUMERIC，其余列用 TEXT，时间列也保持原始文本。未自动清洗百分比、单位和日期。因此这是一套明确类型策略下的执行基线，不宣称还原了官方数据库运行语义。

结果按列位置比对；有顶层 ORDER BY 时保留行顺序，否则按保留重复行数量的集合比对；数值统一到8位小数，NULL与字符串严格区分。每条数据库查询3秒预算，比对上限1000行，超限记录错误。800道 PostgreSQL 参考结果中有156道为空集；并列排序、小数据或空集上的偶然一致不证明查询语义等价。没有逐题人工核验全部参考 SQL 是否真正回答了自然语言问题。

测试器已有13项本地校验覆盖顺序、重复行、NULL、数值与文本区分、中文自关联、三方言参数绑定、结果上限、未知字段和模型请求不携带数据库单元格。Ruff通过。未改动生产代码，因此没有把历史模块回归数量作为本轮测试结果。

完整本地明细在 `.local/dusql-dev-verified/report.json`，最终全量运行约95.47秒。较早的 `.local/dusql-dev-baseline` 使用了 SQLite 默认的双引号字符串回退，会掩盖未知字段错误，**不作为最终证据**；最终已关闭该行为重新核验。

## 真实模型17题结果

使用当时已启用的 `glm-5.3-flash`，每个开发数据库取题号最靠前且通过 PostgreSQL 参考核验的一题。完整 [17道请求内容](examples/dusql-verification/live-request-preview.json) 和 [逐题模型结果及用量](examples/dusql-verification/live-results.json) 已保存。请求包括题目、表字段类型、数据集提供的关联关系、生产探索提示词与 JSON 输出契约；数据库单元格、参考 SQL 和参考结果不外发。

**实际调用17次，无重试，无追加题目，无模型配置切换。** 17次均返回可解析的SQL计划，16题通过编译并实际执行，1题被本地校验拒绝。14题与参考结果一致（其中3题双方均为空集）；2题执行结果不同。参考结果一致率为14/17（82.4%），这是有筛选偏差的小样本指标，不能当作全量准确率。

服务商返回的用量合计：**输入42,717 Token，输出11,818 Token，总计54,535 Token**。逐题计时合计260.17秒，包含本地执行；没有按未知价格推算费用。

| 题号 | 结果 | 核对发现 |
|---|---|---|
| `qid000004` | 与参考不同，参考语义待复核 | 问题是“哪些参考书不是试卷形式”。模型使用 `类型 <> '试卷'`；参考SQL用不在“参考试卷”表中的ID筛选，实际返回了类型为“试卷”的“黄冈试卷”，并排除了类型为“出版书”的“零失误分层训练”。题意、字段类型与跨表数据存在矛盾，不能直接计为模型理解错误。保留原始不一致结果，不改分。 |
| `qid000016` | 模型筛选值错误 | 模型增加 `杯赛 = '欧洲杯'`，实际字段值为“1960年法国欧洲杯”等完整名称，导致反连接排除失效，返回5支球队而非参考的3支。模型缺少枚举值依据却猜测完整取值，需要改进实体/枚举绑定或澄清策略。 |
| `qid000612` | 模型输出不受支持 | 模型为文本收入字段生成了正则运算符 `~`，不在当前查询AST允许列表，编译阶段拒绝。该正则本身是读取表达式，不是一次写入攻击；问题是模型生成能力与校验器支持范围不一致。没有放宽校验或重试。 |

调用复用了生产探索提示词、上下文准备、目录、JSON契约、模型网关和SQL编译器，结果在本地临时表核对。没有走完整API会话、用户权限和Worker调度流程。每题只允许一次输出，区别于产品内可能进行的校验失败后第二次规划。

初次外发动作被自动审批拒绝后未发出请求；用户随后明确授权“模型你可以调用……但是不要乱调”，才执行上述固定17题。当前任务已停止模型调用。

## 复现

在仓库根目录运行，每次选择新的输出目录以保留历史证据：

```powershell
# 离线编译及 SQLite 快照
.venv/Scripts/python.exe scripts/evaluate_dusql.py --output .local/dusql-next
# 同时核验固定本地演示 PostgreSQL，临时表自动回滚
.venv/Scripts/python.exe scripts/evaluate_dusql.py --postgres-local --output .local/dusql-pg-next
# 测试工具自身校验，不连接模型
.venv/Scripts/python.exe -m pytest scripts/tests/test_evaluate_dusql.py -q -p no:cacheprovider
# 本地导出结果和请求预览，不发送请求
.venv/Scripts/python.exe scripts/export_dusql_report.py .local/dusql-pg-next/report.json --output .local/dusql-export-next
```

真实模型执行脚本为 `scripts/evaluate_dusql_live.py`，需传入完整参考报告和新的结果文件路径。脚本拒绝覆盖旧结果，最多17题，不自动重试。后续模型调用应继续遵守已约定的题目与调用量范围。
